# Ethics & GDPR Compliance — energy-big-data

## 1. Data Classification

Smart meter readings (SM-001 to SM-020) are **pseudonymous personal data** under
GDPR Recital 30. Energy consumption patterns can reveal household presence/absence,
daily routines, and occupancy behaviour.

Weather data (WS-MAIN) is not personal data — it is environmental sensor data
with no link to any individual.

Incident reports contain zone-level grid events with no direct personal identifiers.

## 2. Legal Basis

Processing is justified under **Art. 6(1)(f) — legitimate interest** of grid operators
to prevent overload, optimize energy distribution, and maintain grid stability.

The legitimate interest outweighs data subject rights given:
- Data is pseudonymous (no name, address, or direct identifier stored)
- Processing is strictly limited to energy management purposes
- No marketing, profiling, or third-party sharing occurs

## 3. Pseudonymization

Real household identities are replaced with anonymous meter IDs (SM-001 to SM-020)
at the ingestion layer (producer scripts). No mapping table between real identities
and meter IDs is stored in this system.

This satisfies **Art. 25 — Privacy by Design**: pseudonymization is applied
before any data enters the pipeline.

## 4. Data Retention

| Data Type | Retention Period | Justification |
|---|---|---|
| Raw meter readings | 90 days | ML training window |
| 15-minute aggregations | 1 year | Seasonal trend analysis |
| Incident reports | 2 years | Operational and regulatory requirement |
| ML model outputs | 6 months | Prediction audit trail |

After retention period: hard delete from MongoDB collections, not soft-delete.

## 5. Data Subject Rights (Art. 15–20)

- **Right of access (Art. 15):** Meter owner can request all readings for their meter ID
- **Right to erasure (Art. 17):** Data purged within 30 days of verified request
- **Right to portability (Art. 20):** Data exportable as CSV or JSON on request
- **Right to object (Art. 21):** Processing halted for specific meter on request

Note: in this academic simulation, SM-001 to SM-020 are synthetic virtual meters
representing no real individuals. These rights apply in a real deployment.

## 6. Technical Safeguards

- All credentials stored in `.env` — gitignored, never committed to repository
- MongoDB access restricted by username/password (`MONGO_USERNAME`, `MONGO_PASSWORD`)
- Kafka topics accessible only within the Docker internal network (`energy-net`)
- No data transmitted to external services or outside the local deployment
- No plaintext passwords in logs or producer output

## 7. Algorithmic Bias

- Synthetic data generated with realistic distributions across 4 balanced zones (A/B/C/D)
- Forced anomaly injection ensures ~7% anomaly rate across all meter classes
- No demographic variables (age, income, nationality) are collected or inferred
- ML models evaluated on balanced classes — Precision, Recall, F1-Score reported per class

## 8. GDPR Article 25 — Privacy by Design and by Default

| Principle | Implementation |
|---|---|
| Data minimization | Only fields necessary for energy prediction collected |
| Purpose limitation | Data used exclusively for grid optimization and load prediction |
| Pseudonymization | Applied at ingestion layer before data enters Kafka |
| Storage limitation | Explicit retention periods defined (see Section 4) |
| Integrity & confidentiality | Credentials in `.env`, network isolation via Docker |

## 9. Academic Context Disclaimer

This system processes **entirely synthetic data** generated by simulation scripts.
No real household energy data, real meter identifiers, or real personal information
is collected, stored, or processed. GDPR compliance documentation is provided
to demonstrate awareness of real-world deployment requirements.
